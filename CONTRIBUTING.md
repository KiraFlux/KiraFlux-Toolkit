## Основные принципы
- Библиотека **header-only**, написана на **C++17** для **ESP32** (Arduino-среда).
- Используется **CRTP** для статического полиморфизма, вместо виртуальных функций.
- Предпочтение отдаётся `constexpr`, `noexcept`, `[[nodiscard]]` где уместно.
- Обработка ошибок – через `Option<T>` и `Result<T, E>` (без исключений).
- Код должен быть **тестируемым**: модульные тесты в `test/unit/` под `native`, аппаратные тесты в `test/hardware/` (запускаются на esp32).
- Минимизация зависимостей от `Arduino.h` в алгоритмических частях (использовать `std::`, `kf::clamp` и т.д.).

## Работа с репозиторием

### Ветки
- `main` – **стабильная ветка**. Только для релизов. Запрещён прямой push.
- `dev` – **ветка разработки**. Все изменения попадают сюда через squash-merge feature-веток. Защищена от удаления и force push.
- Feature-ветки – именуются `feature/краткое-описание` или `fix/краткое-описание`. Создаются от `dev`.

### Issues и Milestones
- Каждая задача должна быть описана в **Issue**.
- Крупные задачи разбиваются на **подзадачи** (sub‑issues), которые группируются под родительским Issue (meta‑issue).
- Готовые подзадачи помечаются лейблом `ready`.
- Для планирования используются **Milestones** (например, `v0.3.0`).

### Pull Requests
1. Ветка создаётся от актуального `dev`.
2. После завершения работы – открыть Pull Request в `dev`.
3. В описании PR указать, какие Issues закрывает (`Closes #...`).
4. Перед слиянием **обязательно** запустить тесты локально и убедиться, что CI проходит.
5. Слияние в `dev` – **squash and merge** (один коммит с внятным сообщением).
6. После накопления достаточного количества изменений в `dev` создаётся PR в `main` с обычным **merge-коммитом** (не squash). Версия в `library.json` обновляется, создаётся Git-тег.

## Стиль кода

### Форматирование
- Отступы – **4 пробела**, без табуляций.
- Фигурные скобки:
  - На новой строке для определений функций, классов, структур.
  - На той же строке для управляющих конструкций (`if`, `for`, `while`).
- Имена:
  - Классы, структуры, шаблонные параметры – `PascalCase`.
  - Функции, переменные, поля – `snake_case`.
  - Приватные поля – с подчёркиванием в конце (`_field`).
  - Константы и макросы – `UPPER_SNAKE_CASE`.
- Пробелы: вокруг бинарных операторов, после запятых.

### Ключевые правила
- Использовать `[[nodiscard]]` для всех функций, чей результат нельзя игнорировать (например, методы, возвращающие `Option`/`Result`, `bool` успеха).
- По возможности добавлять `constexpr` и `noexcept`.
- В заголовочных файлах избегать `using namespace std;`.
- Для включения стандартных заголовков использовать `#include <...>`, для своих – `#include "..."`.

### Комментарии и документация
- Публичный API должен быть документирован в стиле **Doxygen**:
  ```cpp
  /// @brief Краткое описание.
  /// @param param1 Описание параметра.
  /// @return Описание возвращаемого значения.
  ```
- Комментарии в коде – на **английском**, краткие, объясняющие **почему**, а не что (код говорит сам за себя).
- Внутренние (private) методы можно не документировать, если их назначение очевидно.

## Архитектурные соглашения

### CRTP
Для статического полиморфизма используется CRTP. Базовый класс предоставляет интерфейс, производный реализует детали через `Impl`-методы. Пример:
```cpp
template<typename Impl>
struct Base {
    void doSomething() { impl().doSomethingImpl(); }
private:
    Impl& impl() { return *static_cast<Impl*>(this); }
    const Impl& c_impl() const { return *static_cast<const Impl*>(this); }
};
```

### Опции и Результаты
- `Option<T>` – для опциональных значений (аналог `std::optional`).
- `Result<T, E>` – для операций, которые могут завершиться ошибкой (аналог `std::expected`). Используется вместо исключений.

### Тестируемость
- Код, не зависящий от железа, должен компилироваться и тестироваться в окружении `native`.
- Зависимости от `Arduino.h` сводятся к минимуму: вместо `constrain` используется `kf::clamp`, вместо `map` – `kf::linearMap`, вместо `isnan` – `std::isnan` и т.д.
- Аппаратно-зависимые компоненты (`drivers/`) могут требовать реального железа; для них пишутся интеграционные тесты в `test/hardware/`.

## Процесс разработки

### Шаги для новой фичи или исправления
1. **Создать Issue** (если ещё нет). Для сложной задачи – создать родительское Issue и подзадачи.
2. **Создать ветку** от `dev`:  
   `git checkout dev && git pull && git checkout -b feature/название`
3. **Внести изменения**, следуя стилю кода.
4. **Написать тесты**:
   - Для алгоритмической части – в `test/unit/`.
   - Для нового примера – в `examples/`.
5. **Проверить локально**:  
   `pio test -e native` (и `-e esp32dev`, если есть аппаратные тесты).
6. **Запушить ветку** и создать Pull Request в `dev`.
7. **Дождаться прохождения CI** (GitHub Actions).
8. **Получить апрув** (от себя или другого разработчика) и выполнить **squash merge** в `dev`.
9. **Закрыть связанные Issues** (они закроются автоматически, если в PR указано `Closes #...`).
10. Для дочерних задач в родительском Issue отметить их как готовые (например, комментарием или перемещением в колонку `Ready` на доске проектов).

### Синхронизация с `dev`
Перед созданием PR всегда обновляйте ветку:
```
git fetch origin
git rebase origin/dev
```
Разрешайте конфликты локально. Force-push разрешён только в своих feature-ветках.

## Тестирование

### Модульные тесты (native)
- Располагаются в `test/unit/` с подпапками по модулям (`common/`, `ui/`, `math/` и т.д.).
- Используется фреймворк **Unity**.
- Запуск: `pio test -e native` (должен проходить без ошибок).

### Аппаратные тесты (embedded)
- Для драйверов, требующих реального железа, создаются тесты в `test/hardware/`.
- Запуск на подключённой плате: `pio test -e esp32dev`.
- Если плата не подключена, тесты пропускаются (через `test_ignore` или `test_filter`).

### Примеры
- Каждый пример – отдельный проект в `examples/` со своим `platformio.ini`.
- Пример должен быть **самодостаточным** и демонстрировать использование конкретного компонента.
- Код примера должен быть чистым, с краткими комментариями (на английском).
- После изменений в библиотеке все примеры должны компилироваться (проверяется в CI).

- **CHANGELOG.md** – ведётся при подготовке релиза (фиксируются изменения).

## Версионирование и релизы
- Используется семантическое версионирование **MAJOR.MINOR.PATCH**.
- Версия указывается в `library.json`.
- При несовместимых изменениях API – увеличивается **MAJOR**.
- При добавлении новой функциональности (с обратной совместимостью) – **MINOR**.
- При исправлении ошибок – **PATCH**.
- Перед слиянием `dev` в `main` версия обновляется, создаётся тег (например, `v0.3.0`) и релиз на GitHub.
- **CHANGELOG.md** обновляется с описанием изменений.

## Полезные сценарии

### Как подтянуть изменения из `dev` в свою ветку
```bash
git checkout dev
git pull
git checkout your-feature-branch
git rebase dev
# разрешить конфликты, если есть
git push --force-with-lease
```

### Как создать родительское Issue и подзадачи
1. Создать Issue с меткой `meta` и описанием общей цели.
2. В нём перечислить подзадачи (можно в виде чеклиста).
3. Для каждой подзадачи создать отдельный Issue и связать с родительским (в разделе «Linked pull requests» или через `Parent:` в описании).
4. По мере выполнения помечать подзадачи как `ready` (лейбл) или закрывать их.

### Как закрыть несколько Issues одним PR
В описании PR перечислить все номера:
```
Closes #123, closes #124, closes #125
```
При слиянии они закроются автоматически.
